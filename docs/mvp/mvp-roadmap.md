# AskFlow MVP 로드맵

AskFlow는 자연어로 정형·비정형 보고서를 요청하면 TextToSQL로 데이터를 뽑아 대시보드 화면으로 보여주는 서비스다.
이 문서는 SW 마에스트로 17기 「AI 기반 프로젝트 개발 가이드」의 9단계 흐름을 AskFlow MVP에 적용한 계획이다.
각 단계를 끝낼 때마다 아래 진행 현황을 갱신한다.

## MVP가 증명할 것

> SQL을 모르는 사람이 자연어 질문 하나로 정확한 숫자와 차트가 담긴 보고서를 받는다.

이 문서에서 쓰는 용어 (STEP 2에서 확정한다):

- **정형 보고서:** 항목과 지표가 미리 정해져 있고 주기적으로 반복하는 보고서. 예) 월간 매출 보고서.
- **비정형 보고서:** 그때그때 떠오른 질문으로 만드는 보고서. 예) "지난달 반품이 가장 많았던 상품 5개와 이유는?"

## 빠르게 가기 위한 조정

가이드의 흐름은 그대로 따르되, AskFlow 특성에 맞게 다섯 군데를 바꾼다.

1. **STEP 1~2는 짧게 쓴다.** 목적은 핵심 가설과 Must 기능을 정하는 것이다. 검증 보고서는 1쪽, 경쟁 서비스는 3~5개만 본다.
2. **다이어그램은 레포 안 Mermaid로 그린다.** IA와 아키텍처를 Mermaid로 `docs/`에 두면 GitHub이 바로 그려 주고 Git diff로 변경을 추적할 수 있다. 가이드가 Eraser DSL의 장점으로 든 것과 같다. 발표용 그림이 필요할 때만 Eraser.io나 Whimsical을 쓴다.
3. **STEP 7은 Bolt.new/Lovable 대신 Claude Code로 직접 만든다.** AskFlow의 핵심은 화면이 아니라 TextToSQL 파이프라인(스키마 이해 → SQL 생성 → 검증 → 실행 → 시각화)이다. 가이드도 Bolt.new는 복잡한 DB 연동에 한계가 있다고 적었다. 화면 뼈대만 v0로 뽑고 백엔드와 파이프라인은 처음부터 이 레포에서 만든다. 그러면 MVP 코드가 STEP 9로 버려지지 않고 이어진다.
4. **디자인 토큰은 최소로 한다.** shadcn/ui 기본 토큰에 primary 색만 정하고, 대시보드 화면 3~4개 분량의 컴포넌트만 만든다.
5. **워커는 MVP에서 분리하지 않는다.** 보고서 생성은 API 안에서 동기로 처리하되, 파이프라인을 별도 모듈로 두어 나중에 워커로 옮기기 쉽게 한다. 레포는 하나로 두고 `api/`, `worker/`, `web/` 폴더로 나눈다.

## 실제 데이터로 검증한다

가이드 원칙대로 더미가 아닌 실제 데이터로 테스트한다. TextToSQL은 정확도가 곧 제품 품질이므로 MVP 전에 평가 세트부터 만든다.

- 검증용 데이터셋 하나를 정한다 (결정 필요 1번).
- 그 데이터에 대한 대표 질문 30개 정도와 정답 SQL 또는 정답 값을 만든다. 쉬운 집계, 조인, 기간 비교, 모호한 질문을 섞는다.
- 파이프라인을 고칠 때마다 이 세트를 돌려 정답률을 기록한다. 이 수치가 STEP 1 가설 H1의 근거이자 중간 평가 자료가 된다.

## MVP 범위 초안

STEP 4 PRD에서 확정한다. 가이드 원칙대로 Must는 5개 이하로 둔다.

**Must**

| ID | 기능 | 메모 |
|---|---|---|
| F-001 | 자연어 질문 → SQL 생성 | DB 스키마와 컬럼 설명을 프롬프트에 넣는다 |
| F-002 | SQL 안전 실행 | 읽기 전용 DB 계정, SELECT만 허용, 행 수·실행 시간 제한 |
| F-003 | 결과 표 + 자동 차트 | 결과 형태에 맞는 차트 선택, 생성된 SQL도 함께 보여 줘 근거를 확인할 수 있게 한다 |
| F-004 | 비정형 보고서 | 결과에 대한 자연어 요약과 눈에 띄는 점 |
| F-005 | 정형 보고서 템플릿 1종 | 미리 정한 질문 묶음을 한 번에 실행해 보고서 한 장으로 구성 |

**Should / Could (MVP 이후)**

- 대시보드 저장과 위젯 배치
- 보고서 PDF·Excel 내보내기
- 정형 보고서 예약 생성 (워커 분리 시점)
- 질의 이력, 즐겨찾기
- 모호한 질문에 되묻기
- 여러 DB 연결, 로그인과 권한

**이번 버전 제외**

- 데이터 쓰기 (INSERT, UPDATE, DELETE)
- 실시간 스트리밍 데이터
- 여러 회사가 함께 쓰는 멀티 테넌트

## 핵심 가설 초안

STEP 1에서 다듬고, 수치는 데이터셋을 정한 뒤 확정한다.

- **H1 정확도:** 대표 질문 세트에서 맞는 결과를 내는 비율이 목표치(예: 80%) 이상이다.
- **H2 속도:** SQL을 모르는 사용자가 분석가나 개발자에게 요청하는 기존 방식보다 훨씬 빨리 보고서를 얻는다.
- **H3 신뢰:** 생성된 SQL과 근거를 함께 보여 주면 사용자가 결과를 믿고 그대로 쓴다.

## 결정이 필요한 것

1. **검증용 데이터셋과 도메인:** 공공데이터, 공개 샘플 DB(쇼핑몰·매출 등), 실제 협력 기관 데이터 중 무엇으로 할지. 타겟 유저와 바로 이어진다.
2. **타겟 유저:** 예) 분석가가 없는 소규모 회사 운영자, 사내 영업·기획 담당자.
3. **기술 스택:** 백엔드 언어와 프레임워크, 프론트엔드, 서비스 DB와 분석 대상 DB.
4. **LLM 공급자와 모델.**
5. **일정:** 중간 평가 날짜에서 거꾸로 계산해 STEP 7 마감을 정한다.
6. **팀 구성과 역할:** 팀 프로젝트라면 단계별 담당자.
