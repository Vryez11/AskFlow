# AskFlow MVP 로드맵

AskFlow는 자연어로 요청하면 TextToSQL로 데이터를 뽑아, 정형 보고서는 대시보드로, 비정형 보고서는 문서형 보고서로 보여주는 서비스다.
이 문서는 SW 마에스트로 17기 「AI 기반 프로젝트 개발 가이드」의 9단계 흐름을 AskFlow MVP에 적용한 계획이다.
각 단계를 끝낼 때마다 아래 진행 현황을 갱신한다.

## MVP가 증명할 것

> SQL을 모르는 사람이 자연어 요청 하나로 정확한 숫자와 차트가 담긴 대시보드와 보고서를 받는다.

핵심 산출물은 대시보드와 문서형 보고서다. 결과를 보며 이어지는 질문을 주고받는 챗봇은 MVP 이후에 붙인다.
세 기능은 같은 파이프라인(SQL 생성 → 실행 → 차트)을 쓰므로, 순서를 나눠도 버리는 작업이 없다.

| 구분 | 출력 | 예 |
|---|---|---|
| 정형 보고서 | **대시보드:** 항목과 지표가 정해져 있고 반복해서 본다. KPI 카드와 차트 위젯으로 구성하고, 열 때마다 최신 데이터로 갱신한다 | "주간 매출 대시보드 만들어 줘" |
| 비정형 보고서 | **문서형 보고서:** 그때그때 필요해서 요청하고 읽고 공유한다. 섹션별 차트·표와 서술(발견한 점, 해석, 근거)로 구성한다 | "지난달 반품이 많았던 상품과 지역을 정리해 줘" |

## 빠르게 가기 위한 조정

가이드의 흐름은 그대로 따르되, AskFlow 특성에 맞게 여덟 군데를 바꾼다.

1. **STEP 1~2는 결정에 필요한 만큼만 쓴다.** 목적은 핵심 가설과 Must 기능을 정하는 것이다. 검증 보고서는 결론, 차별점, 가설을 중심으로 쓰고, 경쟁 서비스는 주요한 것만 본다.
2. **다이어그램은 레포 안 Mermaid로 그린다.** IA와 아키텍처를 Mermaid로 `docs/mvp/`에 두면 GitHub이 바로 그려 주고 Git diff로 변경을 추적할 수 있다. 가이드가 Eraser DSL의 장점으로 든 것과 같다. 발표용 그림이 필요할 때만 Eraser.io나 Whimsical을 쓴다.
3. **STEP 7은 Bolt.new/Lovable 대신 Claude Code로 직접 만든다.** AskFlow의 핵심은 화면이 아니라 생성 파이프라인(요청 해석과 계획 → SQL 생성 → 검증 → 실행 → 시각화 → 대시보드·보고서 구성)이다. 가이드도 Bolt.new는 복잡한 DB 연동에 한계가 있다고 적었다. 화면 뼈대만 v0로 뽑고 백엔드와 파이프라인은 처음부터 이 레포에서 만든다. 그러면 MVP 코드가 STEP 9로 버려지지 않고 이어진다.
4. **디자인 토큰은 최소로 한다.** shadcn/ui 기본 토큰에 primary 색만 정하고, 대시보드와 보고서 화면에 필요한 컴포넌트만 만든다.
5. **워커는 MVP에서 분리하지 않는다.** 대시보드·보고서 생성은 API 프로세스 안의 백그라운드 작업으로 처리하되, 파이프라인을 별도 모듈(`pipeline/`)로 두어 나중에 워커로 옮기기 쉽게 한다. 레포는 하나로 두고 `api/`, `pipeline/`, `eval/`, `web/` 폴더로 나누며, `worker/`는 분리할 때 만든다(아키텍처 문서 3장).
6. **데이터 소스는 커넥터 인터페이스로 둔다.** 중소기업의 데이터는 DB, 엑셀, 구글 시트에 흩어져 있다. 데이터를 가져오는 부분을 인터페이스로 정하고 MVP에서는 MySQL 커넥터 하나만 구현한다. 나머지는 같은 인터페이스로 하나씩 붙인다.
7. **기능 명세와 구현은 OpenSpec으로 관리한다.** 가이드는 PRD를 `CLAUDE.md`에 요약하고 Claude Code로 바로 구현하지만, AskFlow는 PRD의 기능 ID마다 OpenSpec change를 만들어 제안 → 구현(`/opsx:apply`) → archive 순서로 진행한다. change의 설계에 기술 스택이 들어가므로 change는 STEP 5 아키텍처를 정한 뒤 만든다. PRD는 MVP 범위를, OpenSpec은 프로젝트 전체의 동작 스펙을 맡는다. 역할과 동기화 규칙은 [conventions/spec.md](../../conventions/spec.md)에 있다.
8. **하네스와 루프로 AI에게 맡긴다.** 가이드는 Claude Code를 쓸 때의 주의사항(기능 하나씩 구현, 코드를 읽고 커밋, 보안 코드 검토)을 사람이 지키게 한다. AskFlow는 이를 자동화한다. 하네스(컨텍스트, 퍼미션, 검증, 도구, 서브에이전트·워크트리, 디버깅)가 일하는 환경과 검사를 갖추고, Ralph 루프가 OpenSpec tasks.md의 작업을 하나씩 구현하고, 구현과 분리된 리뷰어가 검토한다. 하네스는 기술 스택이 정해진 STEP 5 직후, 첫 구현 전에 구성한다. 규칙은 [conventions/harness.md](../../conventions/harness.md)에 있다.

## 실제 데이터로 검증한다

가이드 원칙대로 더미가 아닌 실제 데이터로 테스트한다. TextToSQL은 정확도가 곧 제품 품질이므로 MVP 전에 평가 세트부터 만든다.

**데이터셋**

- 검증용 데이터셋은 [Olist 브라질 이커머스 공개 데이터](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)다. 실제 거래를 익명화한 주문 약 10만 건(2016~2018)이고, 주문·주문 상품·결제·리뷰·고객·판매자·상품 등 9개 테이블로 되어 있다. 판매자가 중소 사업자라 타겟과 맞는다.
- 라이선스가 CC BY-NC-SA 4.0(비상업)이다. 원본은 레포에 커밋하지 않고 다운로드 스크립트로 `data/raw/`에 받는다(`.gitignore`로 제외). 상용 서비스의 데모 데이터로는 쓰지 않는다.
- 개발용 MySQL에 시드 스크립트로 넣고 MySQL 커넥터로 붙인다. 파일럿인 LIT도 MySQL이라 같은 경로를 검증하게 된다.
- 데이터가 2016~2018년이라 "지난 7일" 같은 요청을 하면 결과가 비어 버린다. 그래서 시드할 때 마지막 주문일이 어제가 되도록 날짜를 7일 단위로 옮긴다. 요일은 원본과 같고, 생성되는 SQL은 파일럿과 같이 DB의 오늘 기준으로 계산한다(아키텍처 문서 8장).
- 도시명과 상품 카테고리 값이 포르투갈어라, 한국어 질문과 값을 잇는 용어 사전이 필요하다. MVP에서는 용어 사전을 설정 파일로 넣고, 가설 H5를 시험하는 기회로 쓴다.
- Olist로 검증한 뒤 파일럿(LIT, Nyummy, 주변 창업 프로젝트) 데이터로 넓힌다.

**평가 세트**

- Olist에 대한 대표 질문 30개 정도와 정답 SQL을 만든다. 시드할 때마다 날짜가 옮겨져 정답 값이 바뀌므로, 값을 적어 두지 않고 평가할 때 정답 SQL을 실행해 비교한다. 쉬운 집계, 조인, 기간 비교, 모호한 질문을 섞는다. 대시보드 위젯 하나, 보고서 섹션 하나가 질문 하나에 해당한다.
- 대시보드 요청 5개, 보고서 요청 5개와 각각 기대하는 위젯·섹션 구성도 만든다. 요청 해석과 계획이 쓸 만한지(가설 H6)를 이걸로 잰다.
- 파이프라인을 고칠 때마다 이 세트를 돌려 정답률을 기록한다. 이 수치가 STEP 1 가설 H1의 근거이자 중간 평가 자료가 된다.

## MVP 범위

Must 기능과 수용 기준, 제외 범위의 기준 문서는 [STEP 4 PRD](04-prd.md)다. Should, Could 목록은 [STEP 2 기획서 5장](02-service-plan.md#5-핵심-기능-moscow)에 있다.
가이드 원칙대로 Must는 다섯 개다.

- F-001 요청 해석과 계획
- F-002 SQL 생성
- F-003 SQL 안전 실행과 데이터 연결
- F-004 비정형 보고서
- F-005 정형 대시보드
