# STEP 2. 서비스 기획서

- 작성일: 2026-10-26
- 상태: 초안. 근거는 [STEP 1 검증 보고서](01-idea-validation.md), 진행 계획은 [로드맵](mvp-roadmap.md)에 있다.
- 이 문서는 "무엇을" 만드는지 정한다. "어떻게"는 STEP 4 PRD에서 정한다.

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | AskFlow |
| 한 줄 정의 | SQL을 몰라도 말로 요청하면, 회사 데이터로 대시보드와 보고서를 만들어 주는 B2B 서비스 |
| 슬로건 | 물어보면, 보고서가 된다 |
| 대상 | 전담 데이터 분석가가 없는 중소기업의 운영·기획·영업 담당자 |

**핵심 가치**

1. **기다리지 않는다.** 개발자나 데이터팀에 숫자를 부탁하고 기다리는 대신, 직접 요청해서 몇 분 안에 받는다.
2. **반복하지 않는다.** 매주 같은 쿼리·엑셀·차트 작업 대신, 한 번 만든 대시보드가 열 때마다 최신 데이터로 바뀐다.
3. **믿고 쓴다.** 숫자마다 어떤 데이터로 어떻게 계산했는지 근거가 붙어 있어 그대로 보고에 쓴다.

**결과물**

| 요청 종류 | 결과물 | 쓰임 |
|---|---|---|
| 정형 보고서 | **대시보드:** KPI 카드와 차트 위젯. 열 때마다 최신 데이터 | 반복해서 본다 |
| 비정형 보고서 | **문서형 보고서:** 섹션별 차트·표와 서술(발견한 점, 해석, 근거) | 읽고 공유한다 |

결과를 보며 이어서 묻는 챗봇은 MVP 이후에 붙인다.

## 2. 문제 정의

### 지금의 모습 (예시)

직원 25명인 온라인 쇼핑몰 회사의 운영 매니저가 월요일 회의에 주간 매출을 보고하는 과정이다.

1. 데이터는 자사몰 DB에 있지만 SQL을 몰라 개발자에게 메신저로 부탁한다.
2. 개발자는 기능 개발 중이라 다음 날에야 CSV를 보내 준다.
3. 엑셀에 붙여 넣고 피벗과 차트를 만든다. 지난주 파일을 복사해 숫자만 바꾸는 작업을 매주 반복한다.
4. 회의에서 "지역별로는 어때요?"라는 질문이 나오면 다시 1번으로 돌아간다.

### 문제를 키우는 구조

- **요청을 받아 줄 사람이 부족하다.** 국내 데이터 직무 부족률은 데이터 과학자 31.2%, 분석가 14.2%다(2024 데이터산업 현황조사). 중소기업은 전담 분석가를 두기 어렵다.
- **기존 방법은 이 사람들을 위한 게 아니다.**

| 지금의 방법 | 한계 |
|---|---|
| 개발자에게 부탁 | 기다려야 하고, 개발자는 본업이 밀린다 |
| 엑셀로 직접 | 원본 데이터를 받아야 하고, 매주 같은 작업을 반복한다 |
| BI 도구 도입 | 누군가 대시보드를 미리 만들어야 하고, 새 질문에는 대응하지 못한다 |
| 대형 플랫폼의 AI 분석 (Power BI Copilot, BigQuery 등) | 데이터가 그 플랫폼에 있어야 하고, 라이선스가 비싸다 |
| 오픈소스 GenBI (WrenAI) | 개발자가 에이전트와 Git으로 쓰는 도구라, 현업 담당자가 바로 쓰기 어렵다 |

## 3. 타겟 유저와 페르소나

B2B라서 쓰는 사람과 들이는 사람이 다르다.

- **쓰는 사람:** 운영·기획·영업 담당자와 대표 (P1, P2)
- **들이는 사람:** 대표가 결정하고, 개발자나 IT 담당이 연결과 보안을 맡는다 (P3)

### P1. 김서연, 운영 매니저 (주 사용자)

| 항목 | 내용 |
|---|---|
| 나이·직무 | 31세, 온라인 쇼핑몰 운영 매니저 |
| 회사 | 직원 25명 이커머스 회사. 개발자 2명, 데이터 분석가 없음 |
| 데이터 | 자사몰 MySQL DB (주문, 상품, 고객, 리뷰) |
| 목표 | 매주 월요일 회의에 주간 매출·주문 현황을 보고하고, 프로모션 효과를 빨리 확인한다 |
| 불편함 | SQL을 몰라 숫자 하나에도 개발자를 기다린다. 매주 같은 엑셀 작업을 반복한다 |
| AskFlow로 바뀌는 점 | 주간 매출 대시보드를 한 번 만들어 두고 매주 연다. 궁금한 건 보고서로 요청해 회의 자료로 쓴다 |

### P2. 박준호, 대표 겸 영업 총괄 (주 사용자, 구매 결정자)

| 항목 | 내용 |
|---|---|
| 나이·직무 | 42세, 공동 대표 겸 영업 총괄 |
| 회사 | 직원 60명 B2B 유통 회사. 전산 담당 1명 |
| 데이터 | ERP의 매출 데이터, 엑셀·구글 시트로 관리하는 거래처 목록과 영업 실적 |
| 목표 | 거래처별 매출과 월간 실적을 확인하고, 투자자·이사회 보고 자료를 만든다 |
| 불편함 | 데이터가 여러 곳에 흩어져 있어 월말마다 보고서 작성에 하루를 쓴다 |
| AskFlow로 바뀌는 점 | 월간 실적 대시보드로 숫자를 확인하고, "3월 매출이 왜 떨어졌나" 같은 질문은 보고서로 받는다 |
| 주의 | 데이터가 엑셀·시트에 있어 MVP의 MySQL 커넥터만으로는 온전히 쓸 수 없다. 엑셀·시트 커넥터가 붙은 뒤 본격 대상이 된다 |

### P3. 이도윤, 백엔드 개발자 (도입 담당)

| 항목 | 내용 |
|---|---|
| 나이·직무 | 29세, P1 회사의 백엔드 개발자 |
| 역할 | DB 연결(읽기 전용 계정), 용어 사전 설정, 보안 확인 |
| 목표 | 데이터 추출 요청에서 벗어나 본업에 집중한다 |
| 불편함 | 운영팀의 숫자 요청이 수시로 들어와 개발 흐름이 끊긴다. 회사 DB를 외부 서비스에 연결하는 게 걱정된다 |
| AskFlow로 바뀌는 점 | 한 번 연결하고 용어 사전만 채워 두면 요청이 줄어든다. 읽기 전용, SELECT만 허용, 개인정보 컬럼 가리기로 보안 걱정을 던다 |

파일럿(LIT, Nyummy, 주변 창업 프로젝트)에서는 주로 P1과 P3에 해당하는 사람을 만난다. 대표 혼자 데이터를 보는 작은 팀이라면 한 사람이 P1과 P2를 겸한다.

## 4. 사용 시나리오

### 시나리오 1. 비정형 보고서: 프로모션 효과 정리 (P1)

1. "보고서 만들기"를 고르고 "지난달 프로모션 기간에 매출이 늘어난 카테고리와 지역을 정리해 줘"라고 쓴다.
2. AskFlow가 섹션 3개를 계획한다: 프로모션 전후 카테고리별 매출, 지역별 매출 변화, 요약과 눈에 띄는 점.
3. 섹션마다 차트·표와 서술이 붙은 보고서가 나온다. 숫자 옆의 근거를 펼치면 SQL과 해석한 가정(예: "프로모션 기간은 10월 1~7일로 봤다")이 보인다.
4. "지역은 상위 5개만 보여 줘"라고 수정 요청을 한 줄 적어 다시 만든다.
5. 보고서 링크를 팀 메신저에 공유한다.

### 시나리오 2. 정형 대시보드: 주간 매출 대시보드 (P1)

1. "대시보드 만들기"를 고르고 "매주 월요일에 볼 주간 매출 대시보드 만들어 줘"라고 쓴다.
2. KPI 카드 4개(매출, 주문 수, 평균 주문 금액, 신규 고객 수)와 차트 2개(일별 매출 추이, 카테고리별 매출 상위 5개)가 나온다. 위젯마다 근거를 볼 수 있다.
3. 대시보드를 저장한다.
4. 다음 주 월요일에 열면 지난 7일 데이터로 바뀌어 있다.

### 시나리오 3. 도입과 연결 (P3)

1. 회사 MySQL에 AskFlow용 읽기 전용 계정을 만든다.
2. 연결 정보를 넣는다. MVP에서는 설정 파일로 넣고, 연결 화면은 MVP 이후에 만든다.
3. AskFlow가 테이블과 컬럼 목록을 읽어 온다.
4. 용어 사전에 사내 용어와 컬럼 설명을 적는다. 예) "순매출 = 결제 금액 − 환불 금액", "활성 고객 = 최근 30일 안에 주문한 고객". MVP에서는 설정 파일로 관리한다.
5. 개인정보 컬럼(이름, 전화번호 등)을 지정해 LLM에 보내지 않게 한다.
6. 테스트 요청 몇 개로 결과를 확인하고 운영팀에 넘긴다.

## 5. 핵심 기능 (MoSCoW)

Should, Could, Won't 목록의 기준 문서다. Must 기능은 [PRD](04-prd.md)에서 유저 스토리, 수용 기준과 함께 확정했고, 아래 Must 표는 기획 단계의 요약이다.

### Must (MVP)

| ID | 기능 | 설명 | 시나리오 |
|---|---|---|---|
| F-001 | 요청 해석과 계획 | 사용자가 대시보드와 보고서 중 하나를 고르면, 자연어 요청을 위젯 또는 섹션 2~4개로 나누고 각각 필요한 지표와 질문을 정한다 | 1, 2 |
| F-002 | SQL 생성 | DB 스키마, 컬럼 설명, 용어 사전을 바탕으로 SQL을 만든다. 용어 사전은 설정 파일로 관리한다 | 1, 2, 3 |
| F-003 | SQL 안전 실행과 데이터 연결 | 읽기 전용 계정, SELECT만 허용, 행 수·실행 시간 제한. LLM에는 스키마와 집계 결과만 보내고 개인정보 컬럼은 가린다. 홈에 연결 상태를 보여 준다 | 1, 2, 3 |
| F-004 | 비정형 보고서 | 섹션마다 차트·표와 서술(발견한 점, 해석)을 붙이고, 숫자마다 SQL과 가정을 근거로 보여 준다. 한 줄 수정 요청으로 다시 만들고, 링크로 공유한다 | 1 |
| F-005 | 정형 대시보드 | KPI 카드와 차트 위젯을 고정 그리드로 배치하고 위젯마다 근거를 보여 준다. 한 줄 수정 요청으로 다시 만들고, 저장한 뒤 다시 열면 최신 데이터로 갱신한다 | 2 |

### Should (MVP 직후)

- 챗봇: 결과를 보며 이어지는 질문을 주고받는 대화형 기능 (대화 맥락 유지, 모호한 요청 되묻기)
- 보고서 섹션을 대시보드에 고정하기
- 대시보드 내용을 주간 보고서로 자동 발송 (워커 분리 시점)
- 보고서 PDF 내보내기
- 데이터 소스 연결 화면, 용어 사전·컬럼 설명 편집 화면
- 엑셀·CSV, 구글 시트 커넥터 (P2를 위해). 엑셀 커넥터는 [UCI Online Retail II](https://archive.ics.uci.edu/dataset/502/online+retail+ii)(엑셀 파일 하나, CC BY 4.0)로 시험한다
- 로그인과 권한

### Could

- 대시보드 위젯 자유 배치·편집
- 요청 이력, 즐겨찾기
- 데이터 Excel 내보내기
- 다른 DB 커넥터 (PostgreSQL 등)

### Won't (이번 버전)

- 데이터 쓰기 (INSERT, UPDATE, DELETE)
- 실시간 스트리밍 데이터
- 여러 회사가 함께 쓰는 멀티 테넌트. 파일럿은 회사마다 따로 띄운다

## 6. 차별화 포인트

자세한 경쟁 분석은 [검증 보고서 4장과 6장](01-idea-validation.md#6-askflow의-차별점-가설)에 있다.

| 차별점 | 한 줄 설명 |
|---|---|
| 1. 요청 하나로 대시보드와 보고서를 만든다 | 질문 하나에 답 하나가 아니라, 요청 하나로 위젯·섹션 여러 개의 결과물을 만든다 |
| 2. 반복 지표는 대시보드로 자동화한다 | 한 번 만든 대시보드가 열 때마다 최신 데이터로 갱신된다 |
| 3. 숫자마다 근거를 보여 준다 | SQL, 사용한 테이블·컬럼, 해석한 가정을 붙인다 |

경쟁 서비스와 갈리는 지점은 **누가 쓰는가**다. 대형 플랫폼은 데이터가 자기 웨어하우스에 있어야 하고, WrenAI는 개발자가 에이전트와 Git으로 쓰는 도구다. AskFlow는 현업 담당자가 화면에서 바로 쓰고, 비정형 요청은 문서형 보고서로 받는다.

## 7. 비즈니스 모델

- **형태:** 회사 단위 구독형 B2B SaaS.
- **과금 가설:** 회사당 월정액에 사용량 상한(월 생성 수, 데이터 소스 수)을 둔다. 사용자 수로 과금하면 보는 사람이 늘수록 비싸져서, 공유가 핵심인 보고서와 맞지 않는다.
- **비교 기준:** Power BI Pro는 사용자당 월 14달러에 Copilot용 Fabric 용량이 따로 든다. ThoughtSpot은 사용자당 월 25~50달러다(자료마다 다름).
- **변동비:** LLM 호출 비용이다. MVP에서 대시보드·보고서 1건당 LLM 비용을 재서 가격 하한을 정한다.
- **MVP 단계:** 파일럿은 무료로 하고, 인터뷰에서 지불 의사를 확인한다.
  - 이게 없으면 지금 이 일에 한 달에 몇 시간을 쓰나요?
  - 월 얼마면 바로 쓰겠고, 얼마부터 고민되나요?
  - 도입은 누가 결정하나요?
- **확장:** 중견·대기업 현업 부서, 이후 공공기관으로 넓힌다. 공공기관은 설치형 배포와 자체 호스팅 LLM이 필요해 별도 준비가 든다.

## 8. 아직 불명확한 것

팀원마다 다르게 해석할 수 있거나 아직 답이 없는 부분이다. 파일럿과 PRD에서 정한다.

1. **대시보드·보고서 선택:** 사용자가 직접 고르게 했는데, 실제 사용자가 이 구분을 자연스럽게 받아들일지는 파일럿에서 관찰한다.
2. **용어 사전은 누가 채우나:** MVP에서는 설정 파일이라 P3(개발자) 몫이다. 편집 화면이 생기면 현업이 직접 고치게 할지 정한다.
3. **보고서 공유 범위:** MVP에는 로그인이 없어 링크를 아는 사람은 누구나 본다. 파일럿은 회사마다 따로 띄우고 접근을 제한한다.
4. **가격과 지불 의사:** 7장의 인터뷰 질문으로 확인한다.
5. **데이터가 엑셀·시트에 있는 회사의 비중:** P2 같은 회사가 많다면 엑셀·시트 커넥터를 앞당긴다.
