# STEP 4. PRD (MVP)

- 작성일: 2026-10-26
- 상태: 초안. MVP의 Must 기능과 수용 기준은 이 문서가 기준이다.
- 역할: [스펙 관리 규칙](../../conventions/spec.md)에 따라 MVP의 "왜, 무엇을, 어디까지"를 다룬다. 시스템 동작 스펙(요구사항, WHEN/THEN 시나리오, 설계)은 기능 ID별 OpenSpec change에서 쓴다.

## 1. 프로덕트 개요

> SQL을 모르는 사람이 자연어 요청 하나로 정확한 숫자와 차트가 담긴 대시보드와 보고서를 받는다.

| 항목 | 내용 |
|---|---|
| 대상 | 전담 데이터 분석가가 없는 중소기업의 운영·기획·영업 담당자 (기획서 페르소나 P1, P2). 연결과 보안은 개발자가 맡는다 (P3) |
| 결과물 | 정형 보고서는 **대시보드**, 비정형 보고서는 **문서형 보고서** |
| MVP 데이터 | Olist 공개 데이터를 넣은 MySQL, 이후 파일럿(LIT, Nyummy, 주변 창업 프로젝트) |
| MVP에서 빠지는 것 | 챗봇, 로그인, 엑셀·시트 커넥터 등 (6장) |

## 4. 유저 스토리와 수용 기준

수용 기준은 사용자 관점에서 확인할 수 있게 쓴다. 시스템이 어떻게 그렇게 하는지는 OpenSpec change에서 정한다.

### F-001. 요청 해석과 계획

**유저 스토리:** 운영 매니저(P1)로서, 대시보드와 보고서 중 무엇을 만들지 고르고 평소 말로 요청하고 싶다. 그래야 SQL 없이 필요한 결과를 받을 수 있다.

**수용 기준**

- [ ] 홈에서 "대시보드 만들기"와 "보고서 만들기" 중 하나를 고르고 요청을 입력할 수 있다.
- [ ] 요청을 보내면 결과 화면으로 이동하고, 만드는 동안 계획한 위젯 또는 섹션 목록과 진행 상황이 보인다.
- [ ] 계획은 위젯 또는 섹션 2~4개로 이루어진다.
- [ ] 요청이 연결된 데이터로 답할 수 없는 내용이면, 결과를 만들지 않고 이유와 요청을 고칠 방법을 보여 준다.
- [ ] 요청을 해석하며 정한 가정(기간, 지표의 정의 등)은 결과의 근거 패널에 남는다.

### F-002. SQL 생성

**유저 스토리**

- 운영 매니저(P1)로서, 위젯과 섹션마다 필요한 숫자가 정확히 뽑히기를 원한다. 그래야 개발자에게 다시 부탁하지 않아도 된다.
- 개발자(P3)로서, 사내 용어와 컬럼 설명을 설정 파일에 적어 두고 싶다. 그래야 운영팀이 쓰는 말로 요청해도 맞는 결과가 나온다.

**수용 기준**

- [ ] 위젯·섹션마다 연결된 MySQL에서 실행할 수 있는 SELECT 문이 하나씩 만들어진다.
- [ ] 설정 파일의 용어 사전과 컬럼 설명이 결과에 반영된다. 예) 용어 사전에 "순매출 = 결제 금액 − 환불 금액"이 있으면, "순매출" 요청은 이 정의대로 계산된다.
- [ ] 용어 사전 설정 파일을 고치고 앱을 다시 시작하면 다음 요청부터 반영된다.
- [ ] 평가 세트를 용어 사전을 켠 상태와 끈 상태로 각각 돌려 정답률을 비교할 수 있다.

### F-003. SQL 안전 실행과 데이터 연결

**유저 스토리:** 개발자(P3)로서, AskFlow가 회사 DB를 바꾸거나 무겁게 만들지 않고 개인정보를 밖으로 보내지 않기를 원한다. 그래야 안심하고 연결할 수 있다.

**수용 기준**

- [ ] 연결 정보는 설정 파일로 넣는다. 연결할 때 계정에 쓰기 권한이 있으면 홈에 경고가 보인다.
- [ ] SELECT가 아닌 SQL(INSERT, UPDATE, DELETE, DDL 등)은 실행되지 않고 오류로 표시된다.
- [ ] 한 번에 가져오는 행 수와 실행 시간에 상한이 있다. 넘으면 중단되고, 그 사실이 화면에 보인다. 상한 값은 설정으로 바꿀 수 있다.
- [ ] 설정 파일에 지정한 개인정보 컬럼의 값은 LLM에 보내지 않는다.
- [ ] 홈에 데이터 연결 상태(연결 여부, 테이블 수, 용어 수)가 보인다. 연결에 실패하면 원인과 확인할 설정이 보인다.

### F-004. 비정형 보고서

**유저 스토리:** 운영 매니저(P1)로서, 궁금한 것을 요청하면 회의에 바로 쓸 수 있는 보고서를 받고 싶다. 그래야 데이터를 받아 엑셀로 정리하는 일을 하지 않아도 된다.

**수용 기준**

- [ ] 섹션마다 제목, 차트 또는 표, 서술(발견한 점과 해석)이 있다.
- [ ] 차트 종류는 결과 형태에 맞게 고른다. 예) 시간에 따른 변화는 선 차트, 항목 비교는 막대 차트.
- [ ] 섹션마다 근거를 열면 SQL, 사용한 테이블·컬럼, 해석한 가정이 보인다.
- [ ] 서술에 나오는 숫자는 모두 그 섹션의 결과에 있는 값이다.
- [ ] 가정이 여러 개이거나 결과가 비어 있으면 근거 패널에 경고가 보인다.
- [ ] 수정 요청을 한 줄 적으면 새 보고서가 만들어지고, 원래 보고서는 그대로 남는다.
- [ ] 보고서마다 고유한 주소가 있어 링크를 복사해 공유할 수 있고, 링크를 연 사람은 같은 내용을 본다.
- [ ] 일부 섹션이 실패해도 나머지 섹션은 보이고, 실패한 섹션만 오류로 표시된다.
- [ ] 만든 보고서는 홈의 최근 보고서 목록에 나온다.

### F-005. 정형 대시보드

**유저 스토리:** 운영 매니저(P1)로서, 매주 보는 지표를 대시보드로 한 번 만들어 두고 열 때마다 최신 숫자를 보고 싶다. 그래야 매주 같은 엑셀 작업을 반복하지 않는다.

**수용 기준**

- [ ] KPI 카드와 차트 위젯이 고정 그리드에 배치된다.
- [ ] 위젯마다 근거(SQL, 사용한 테이블·컬럼, 해석한 가정)를 열 수 있다.
- [ ] 수정 요청을 한 줄 적으면 새 대시보드가 만들어진다.
- [ ] 저장하면 홈의 저장한 대시보드 목록에 새 대시보드로 추가된다.
- [ ] 저장한 대시보드를 다시 열면 위젯 구성은 그대로이고 숫자만 최신 데이터로 바뀐다.
- [ ] "지난 7일"처럼 상대적인 기간은 여는 날의 기준 날짜로 계산된다. 기준 날짜를 어떻게 정할지(Olist 데이터 포함)는 STEP 5에서 정한다.
- [ ] 일부 위젯이 실패해도 나머지 위젯은 보이고, 실패한 위젯만 오류로 표시된다.

## 5. 비기능 요구사항

| 항목 | 요구사항 |
|---|---|
| 성능 | 대시보드·보고서 생성 1회는 2분 안에 끝나는 것을 목표로 한다. 저장한 대시보드 다시 열기는 5초 안이 목표다. MVP에서 재 보고 조정한다 |
| 보안 | F-003의 기준을 따른다. DB 비밀번호 같은 비밀 값은 `.env`로 두고 커밋하지 않는다 |
| 접근 | 로그인이 없으므로 파일럿은 회사마다 따로 띄우고 접근을 제한한다 |
| 측정 기록 | 2장의 기록(요청·완성 시각, 수정 요청 횟수, 대시보드 저장·열람)을 남긴다. 기록에 개인정보는 넣지 않는다 |
| 평가 | 평가 세트를 자동으로 돌려 정답률을 기록할 수 있다 |
| 환경 | 데스크톱 브라우저를 기준으로 한다. 화면과 요청은 한국어다 |

## 6. 제외 범위

이번 MVP에서는 하지 않는다. 이후 계획은 [기획서 5장](02-service-plan.md#5-핵심-기능-moscow)의 Should, Could에 있다.

- 챗봇 (결과를 보며 이어서 묻기, 되묻기)
- 로그인과 권한
- 데이터 소스 연결 화면, 용어 사전 편집 화면 (MVP는 설정 파일)
- 엑셀·CSV, 구글 시트, MySQL 외 DB 커넥터
- 보고서 섹션을 대시보드에 고정하기, 위젯 자유 배치, 대시보드 덮어쓰기 저장
- 보고서 PDF 내보내기, 주간 보고서 자동 발송
- 모바일 화면 최적화
- 데이터 쓰기, 실시간 스트리밍 데이터, 멀티 테넌트

## 7. OpenSpec change 계획

기능 ID마다 change를 하나씩 만든다. 설계(design.md)에 기술 스택이 들어가므로 **STEP 5 아키텍처를 정한 뒤** 만든다.
아래 순서는 서로 기대는 순서다. 앞의 change가 있어야 뒤의 change를 확인할 수 있다.

| 순서 | change (안) | 기능 | 메모 |
|---|---|---|---|
| 1 | `add-safe-sql-execution` | F-003 | 연결, 연결 상태, 안전 실행 |
| 2 | `add-sql-generation` | F-002 | 용어 사전, 평가 세트 실행 도구 포함 |
| 3 | `add-request-planning` | F-001 | 요청 화면과 계획 |
| 4 | `add-unstructured-report` | F-004 | 보고서 화면, 근거 패널, 공유 링크 |
| 5 | `add-structured-dashboard` | F-005 | 대시보드 화면, 저장과 다시 열기 |

API와 데이터 구조는 각 change의 설계에서 정한다.

## 8. 검토하며 정한 것과 남은 것

가이드의 권장대로 "개발자 입장에서 불명확한 부분"을 찾아 정리했다.

**정한 것**

| 불명확했던 것 | 결정 |
|---|---|
| IA에서 미뤄 둔 연결 상태 표시는 어느 기능인가 | F-003에 넣고 기능 이름을 "SQL 안전 실행과 데이터 연결"로 넓혔다 |
| "숫자마다 근거"의 단위 | 근거는 섹션·위젯 단위로 열고, 서술에 나오는 숫자는 그 섹션의 결과에 있는 값만 쓴다 |
| 용어 사전 변경은 언제 반영되나 | 앱을 다시 시작하면 반영된다 (MVP) |
| 상대 기간("지난 7일")의 기준 | 여는 날의 기준 날짜로 계산한다. 정하는 방식은 STEP 5 |

**남은 것 (OpenSpec 설계에서 정한다)**

- 행 수와 실행 시간 상한의 기본값
- 쓰기 권한이 있는 계정을 어떻게 알아낼지
- 성능 목표가 실제로 맞는지 (MVP에서 재고 조정)
