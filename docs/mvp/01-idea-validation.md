# STEP 1. 아이디어 검증 보고서

- 작성일: 2026-10-26
- 상태: 초안. 타겟 유저는 A(중소기업, B2B), 출력 구조는 정형은 대시보드·비정형은 문서형 보고서, 검증용 데이터셋은 Olist로 확정했다. 가설 수치는 Olist 평가 세트를 만든 뒤 확정한다.
- 아이디어: 자연어로 요청하면 TextToSQL로 데이터를 뽑아, 정형 보고서는 대시보드로, 비정형 보고서는 문서형 보고서로 보여준다.

## 결론

문제는 실재하고 시장도 커지고 있다. 하지만 **"자연어로 SQL 만들기" 자체는 더 이상 차별점이 아니다.**
Google, Microsoft, Snowflake, Databricks가 이미 자기 데이터 플랫폼에 같은 기능을 넣었고, 오픈소스 WrenAI도 있다.

그래서 AskFlow는 아래 세 가지에 집중해야 한다.

1. **자연어 요청 하나로 대시보드와 보고서를 만든다.** 정형 보고서는 반복해서 보는 대시보드로, 비정형 보고서는 읽고 공유하는 문서형 보고서로 만든다. 질문을 주고받는 챗봇은 경쟁 서비스가 이미 다 하므로 MVP 이후에 붙인다.
2. 한 번 보고 끝나는 결과가 아니라 **반복해서 보는 지표를 대시보드로 자동화**한다. 열 때마다 최신 데이터로 갱신된다.
3. 숫자의 **근거(SQL, 쓴 테이블, 가정)를 보여 줘서** 그대로 보고에 쓸 수 있게 한다.

| 구분 | 출력 | 사용자가 하는 일 |
|---|---|---|
| 정형 보고서 | **대시보드:** KPI 카드와 차트 위젯. 열 때마다 최신 데이터 | 반복해서 본다 (모니터링) |
| 비정형 보고서 | **문서형 보고서:** 섹션별 차트·표와 서술(발견한 점, 해석, 근거) | 읽고 공유한다 (보고, 회의) |

대상은 전담 분석가가 없는 중소기업이고, 데이터가 있는 곳(DB, 엑셀, 구글 시트)에 바로 연결해 쓴다.
MVP는 이 방향이 실제로 먹히는지를 가설 H1~H6으로 검증한다.

## 1. 핵심 페인포인트

| 문제 | 근거 |
|---|---|
| SQL을 모르면 원하는 숫자를 직접 못 뽑고, 개발자·데이터팀에 요청한 뒤 기다려야 한다 | 데이터팀이 업무 시간의 최대 절반을 이런 단발성 요청에 쓴다는 업계 글이 있다 (출처가 불분명해 참고만) |
| 요청을 받아 줄 데이터 인력 자체가 부족하다 | 국내 데이터 직무 부족률: 데이터 과학자 31.2%, 분석가 14.2%. 채용 애로 1위는 "실무 역량 갖춘 인력 부족" 62.3% (2024 데이터산업 현황조사) |
| 주간·월간 보고서는 매번 같은 쿼리, 엑셀 복사, 차트 작업을 반복한다 | 정형 보고서의 특성. 사용자 인터뷰로 확인 필요 |
| BI 도구를 도입해도 대시보드를 미리 만들어 둬야 하고, 새 질문에는 대응하지 못한다 | 조직 내 BI 도구 실사용률이 20~26%에 머문다는 업계 자료 (2차 인용이라 참고만) |

## 2. 타겟 유저 후보

| 후보 | 상황 | 장점 | 단점 |
|---|---|---|---|
| **A. 전담 분석가가 없는 중소기업의 운영·기획·영업 담당자** | 데이터가 운영 DB, 엑셀, 구글 시트에 흩어져 있고, 주간·월간 보고서를 직접 만든다 | 고통이 가장 크고 기존 BI가 없다 | 데이터 소스가 제각각이다. 지불 의사와 보안 우려를 확인해야 한다 |
| B. 데이터팀이 있는 중견·대기업 현업 부서 | 요청이 데이터팀에 몰려 병목이 생긴다 | 요청 병목이 뚜렷하다 | 이미 Power BI·Looker 등을 쓰고 있고, 보안 심사가 길다 |
| C. 공공기관·지자체 담당자 | 공공데이터로 정기 보고서를 만든다 | 공개 데이터로 바로 실험할 수 있다 | 도입 절차가 길고 MVP 피드백을 받기 어렵다 |

**확정: A, B2B 서비스.** 기존 도구가 비어 있는 자리다. 회사 단위로 판매하고, 실제로 쓰는 사람은 운영·기획·영업 담당자, 도입을 결정하는 사람은 대표나 IT 담당이다.

초기 검증은 공개 데이터로 시작하고, 운영 중인 LIT·Nyummy와 주변 창업 프로젝트를 파일럿으로 삼는다. 셋 다 분석가가 없는 소규모 회사라 A의 상황과 같다.
다만 LIT·Nyummy는 직접 만든 서비스라 스키마를 너무 잘 알아서 결과가 좋게 나오기 쉽다. 외부 파일럿을 최소 한 곳은 둔다.

## 5. 최근 1년 트렌드

1. **대화형 분석이 기본 기능이 됐다.** Google은 2026년 6월 BigQuery·Looker용 Conversational Analytics API를 정식 출시했고, Power BI·Snowflake·Databricks도 같은 기능을 갖췄다. 자연어 질의만으로는 차별화가 안 된다.
2. **정확도는 모델보다 맥락에서 나온다.** WrenAI와 Cortex Analyst는 시맨틱 모델(업무 정의, 허용된 조인, 단위)을 먼저 만든다. 국내 구축 사례도 SQL 생성보다 데이터·메타데이터 품질이 성능을 좌우한다고 본다.
3. **벤치마크는 오르지만 사람과 격차가 있다.** BIRD 1위는 83.40%(2026년 9월)이고 사람은 92.96%다. 실무형 벤치마크 Spider 2.0은 공개 당시 o1-preview가 21.3%만 풀었을 만큼 어렵다.
4. **답의 형태가 SQL에서 차트, 서술형 인사이트, 대시보드로 넓어졌다.** 국내외 생성형 BI 제품이 그래프, KPI, 설명을 한 번에 주고, WrenAI는 에이전트가 대시보드를 만들어 배포까지 한다.
5. **오픈소스가 재편 중이다.** 대표 오픈소스였던 Vanna(GitHub 별 약 2.4만)는 저장소가 보관(archived) 처리됐다.

## 6. AskFlow의 차별점 (가설)

결론의 세 가지가 곧 차별점이다.

| 차별점 | 경쟁 서비스와의 차이 | 검증 가설 |
|---|---|---|
| 1. 자연어 요청 하나로 대시보드와 보고서를 만든다 | 경쟁 서비스는 대부분 질문 하나에 답 하나를 주는 질의응답(챗봇) 중심이고, 기존 BI는 사람이 대시보드를 직접 만들어야 한다. AskFlow는 요청 하나로 대시보드(위젯 여러 개)나 문서형 보고서(섹션 여러 개)를 만든다 | H6, H2 |
| 2. 반복해서 보는 지표를 대시보드로 자동화한다 | 대화형 분석은 매번 다시 물어야 한다. WrenAI도 에이전트로 대시보드를 만들지만 개발자용이다. AskFlow는 현업 담당자가 화면에서 요청한 정형 보고서를 대시보드로 저장해 두고, 열 때마다 최신 데이터로 갱신한다 | H4 |
| 3. 숫자의 근거를 보여 준다 | 생성 SQL을 보여 주는 도구는 이미 있다. AskFlow는 대시보드 위젯과 보고서 안의 숫자마다 SQL, 사용한 테이블·컬럼, 해석한 가정을 붙여 그대로 보고에 쓸 수 있게 한다 | H3 |

세 가지를 받쳐 주는 것 (차별점이라기보다 갖춰야 할 조건):

- **데이터가 있는 곳에 바로 연결:** 대형 플랫폼은 자기 웨어하우스에 데이터가 있어야 한다. AskFlow는 DB, 엑셀, 구글 시트를 데이터 소스 커넥터로 붙인다.
- **한국어 업무 용어 사전:** 컬럼 설명과 사내 용어("활성 고객", "순매출" 등)를 등록해 정확도를 올린다(H5). 시맨틱 레이어의 가벼운 버전이다.

반론: WrenAI는 SQL 생성, 차트, 인사이트, 시맨틱 레이어에 더해 에이전트로 대시보드를 만들어 배포하는 기능까지 갖췄다(2026-10-26 README 기준). 그래서 "자연어로 대시보드 만들기"만으로는 WrenAI와 갈리지 않는다.
차별점은 개발자가 아닌 현업 담당자가 화면에서 바로 쓴다는 점, 비정형 요청을 문서형 보고서로 만든다는 점, 타겟 A를 위한 쉬운 설치에 달려 있다. H6과 H4로 반드시 검증한다.

## 7. 큰 리스크와 대응

| 리스크 | 대응 |
|---|---|
| **틀린 숫자.** 대시보드나 보고서에 잘못된 값이 들어가면 신뢰가 바로 무너진다 | 대표 질문 평가 세트로 정답률을 계속 잰다. SQL과 근거를 노출한다. 모호한 요청은 해석한 가정을 대시보드와 보고서에 적고(되묻기는 챗봇과 함께 MVP 이후), 확신이 낮으면 경고한다 |
| **보안과 개인정보.** 회사 데이터를 외부 LLM에 연결하는 거부감, 잘못된 쿼리로 인한 DB 부하, 고객 개인정보 노출 | 읽기 전용 계정만 받는다. SQL 파서로 SELECT만 허용하고 행 수·실행 시간을 제한한다. LLM에는 스키마와 집계 결과만 보내고, 개인정보 컬럼은 가린다 |
| **차별화 실패.** 대형 플랫폼과 오픈소스 사이에서 설 자리가 없다 | 타겟을 A로 좁히고, 챗봇이 아닌 대시보드·보고서 생성에 집중한다. H4가 실패하면 방향을 다시 잡는다 |

## 8. MVP에서 검증할 핵심 가설

수치는 목표치 초안이다. Olist 평가 세트를 만든 뒤 확정한다.

| ID | 가설 | 검증 방법 | 성공 기준 (초안) |
|---|---|---|---|
| H1 | 단일 도메인 DB에서 실무에 쓸 만한 정확도가 나온다 | 대표 질문 30개 평가 세트 | 정답률 80% 이상 |
| H2 | SQL을 모르는 사용자가 기존 방식보다 훨씬 빨리 대시보드·보고서를 얻는다 | 테스트 사용자에게 같은 과제를 주고 시간 측정 | 요청부터 대시보드·보고서까지 5분 이내 |
| H3 | 근거를 보여 주면 사용자가 결과를 믿고 그대로 쓴다 | 테스트 후 설문, 수정 요청 비율 | 테스트 사용자 과반이 "그대로 쓰겠다" |
| H4 | 저장한 대시보드를 반복해서 연다 | 파일럿 조직의 대시보드 저장 수와 재방문 횟수 | 파일럿 기간 중 저장한 대시보드를 주 1회 이상 다시 여는 사용자가 생긴다 |
| H5 | 컬럼 설명과 용어 사전이 정확도를 크게 올린다 | 평가 세트를 메타데이터 있음·없음으로 비교 | 정답률 10%p 이상 상승 |
| H6 | 자연어 요청 하나로 사용자가 기대한 구성의 대시보드·보고서가 나온다 | 대시보드 요청 5개, 보고서 요청 5개에 대해 사용자가 위젯·섹션 구성을 평가 | 수정 요청 1회 이내로 쓸 만한 결과가 나오는 비율 70% 이상 |

## 9. 다음 단계로 넘길 것

- **확정:** 검증용 데이터셋은 Olist 브라질 이커머스 공개 데이터, 첫 커넥터는 MySQL이다. 자세한 내용은 [로드맵](mvp-roadmap.md#실제-데이터로-검증한다)에 있다.
- **아키텍처에 반영:** 데이터를 가져오는 부분을 데이터 소스 커넥터 인터페이스로 둔다. DB, 엑셀·CSV, 구글 시트는 이 인터페이스의 구현체로 하나씩 붙이고, MVP에서는 MySQL 커넥터만 구현한다.
- **STEP 2 기획서에 반영:** 정형은 대시보드·비정형은 문서형 보고서라는 구조, 챗봇은 MVP 이후라는 순서, 차별점 3가지와 이를 받쳐 주는 데이터 연결·용어 사전, 리스크 대응.
- **용어 사전:** H5를 검증하려면 MVP에도 필요하다. MVP에서는 설정 파일로 넣고, 편집 화면은 Should로 둔다.
