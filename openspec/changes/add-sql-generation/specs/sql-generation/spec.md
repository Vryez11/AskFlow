# Spec Delta

## Purpose

위젯·섹션의 질문 하나를 연결된 MySQL에서 실행할 수 있는 SELECT 문 하나로 바꾸고, F-003의 안전 실행 경로로 실행한다. 목표와 수용 기준은 PRD F-002를 따른다.

## ADDED Requirements

### Requirement: 질문 하나에 SELECT 하나 (F-002)

시스템은 질문 하나를 받아 SELECT 문 하나와 그 SQL이 기대는 가정 목록을 만들어야 한다(SHALL). 만든 SQL은 F-003의 안전 실행 경로로만 실행하고, 생성 결과로 SQL, 가정, 실행 결과 또는 실행 오류, 시도 횟수를 돌려주어야 한다(SHALL).

#### Scenario: 집계 질문
- **WHEN** "주문 상태별 주문 수"를 묻는다
- **THEN** SELECT 문 하나와 가정 목록이 만들어지고, 안전 실행 경로로 실행한 결과가 함께 돌아온다

#### Scenario: 가정
- **WHEN** 질문에 기준이 빠져 있어 LLM이 기준을 정해 SQL을 만든다(예: "매출"을 결제 금액 합계로 봄)
- **THEN** 그 기준이 가정 목록에 한국어 문장으로 들어 있다

### Requirement: 생성에 쓰는 정보 (F-002)

시스템은 SQL을 만들 때 LLM에 허용 테이블의 테이블 이름, 컬럼 이름과 형, 설정한 컬럼 설명, 켜져 있으면 용어 사전, 질문을 보내야 한다(SHALL). 허용하지 않은 테이블과 그 컬럼은 보내지 않아야 한다(SHALL NOT). 상대적인 기간("지난 7일", "이번 달")은 DB의 오늘(`CURDATE()`)을 기준으로 계산하라고 알려야 한다(SHALL).

#### Scenario: 허용 테이블만 알림
- **WHEN** 허용 테이블이 orders와 customers인 DB에서 SQL을 만든다
- **THEN** LLM에 보낸 요청에는 두 테이블과 그 컬럼만 있고, 다른 테이블 이름은 없다

#### Scenario: 컬럼 설명
- **WHEN** 설정에 `orders.order_status`의 설명이 있다
- **THEN** LLM에 보낸 요청에 그 설명이 그 컬럼과 함께 있다

#### Scenario: 상대 기간
- **WHEN** "지난 7일 주문 수"를 묻는다
- **THEN** LLM에 보낸 요청에 기간을 DB의 오늘(`CURDATE()`) 기준으로 계산하라는 규칙이 있다

### Requirement: 실행이 실패하면 고쳐 다시 만든다 (F-002)

검사나 실행이 실패하면 시스템은 이전 SQL과 LLM에 보낼 수 있는 실행 오류를 넘겨 고친 SQL을 다시 받아야 한다(SHALL). 처음 시도를 포함해 최대 3번 시도하고, 끝까지 실패하면 마지막 실행 오류를 돌려주어야 한다(SHALL). 연결 실패는 SQL 문제가 아니므로 고치지 않고 바로 돌려주어야 한다(SHALL).

#### Scenario: 없는 컬럼을 고침
- **WHEN** 첫 SQL이 없는 컬럼을 써서 "DB 오류"가 나고, 고친 SQL은 실행된다
- **THEN** 결과가 돌아오고 시도 횟수는 2다

#### Scenario: 끝까지 실패
- **WHEN** 세 번 모두 검사나 실행이 실패한다
- **THEN** 마지막 실행 오류가 돌아오고 시도 횟수는 3이며, 네 번째 요청은 보내지 않는다

#### Scenario: 연결 실패
- **WHEN** 실행 결과가 "연결 실패"다
- **THEN** LLM에 고쳐 달라고 하지 않고 바로 연결 실패를 돌려준다

#### Scenario: 고치기 요청에 DB 원문 없음
- **WHEN** "DB 오류"로 고쳐 달라고 요청한다
- **THEN** LLM에 보낸 요청에는 오류 종류, 한국어 메시지, 오류 코드만 있고 DB가 알려 준 오류 원문은 없다

### Requirement: SQL 생성 단계는 결과 값을 LLM에 보내지 않음 (F-002)

SQL을 만들고 고치는 동안 시스템은 실행 결과의 값을 LLM에 보내지 않아야 한다(SHALL NOT). 결과를 LLM에 보내는 일(보고서 서술)은 F-004에서 F-003의 "LLM에 보낼 결과"로만 한다.

#### Scenario: 행 수 상한 초과를 고침
- **WHEN** 첫 SQL이 행 수 상한을 넘어 다시 만든다
- **THEN** LLM에 보낸 고치기 요청에는 상한 값과 오류 종류만 있고 결과 행은 없다

### Requirement: 실행 기록 (F-002)

시스템은 생성 요청마다 기록 ID를 붙여 질문, 용어 사전 사용 여부, 시도마다 생성 SQL·가정·오류 종류, 실행 결과의 행 수와 열 이름, 실제로 답한 LLM 공급자와 모델, 걸린 시간을 파일로 남겨야 한다(SHALL). 결과 값, 비밀번호, API 키는 남기지 않아야 한다(SHALL NOT). 기록 ID로 같은 질문과 같은 용어 사전 설정의 생성을 다시 돌릴 수 있어야 한다(SHALL).

#### Scenario: 기록을 남김
- **WHEN** 질문 하나로 SQL을 만들고 실행한다
- **THEN** 기록 파일에 질문, 시도별 SQL, 행 수, 열 이름, 공급자와 모델이 있다

#### Scenario: 값은 남기지 않음
- **WHEN** 실행 결과에 행이 있다
- **THEN** 기록 파일에는 행 수와 열 이름만 있고 결과 값은 없다

#### Scenario: 요청 하나 재현
- **WHEN** 기록 ID로 다시 돌린다
- **THEN** 같은 질문과 같은 용어 사전 설정으로 다시 만들고, 새 기록 ID로 따로 남긴다
