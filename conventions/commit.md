# 커밋 컨벤션

## 형식

```
<type>(<scope>): <요약> (F-001)

<본문: 왜 바꿨는지 (선택)>
```

- 요약은 한국어로, "~한다"로 끝나는 현재형 문장으로 쓴다. 마침표는 찍지 않는다.
- 무엇을 건드렸는지보다 무엇이 달라지는지가 보이게 쓴다.
- PRD 기능과 관련 있으면 끝에 기능 ID를 괄호로 붙인다. 여러 개면 `(F-001, F-003)`.
- 여러 영역에 걸친 변경이면 scope를 생략한다.

## type

| type | 언제 |
|---|---|
| feat | 사용자가 체감하는 기능을 추가하거나 바꿀 때 |
| fix | 버그를 고칠 때 |
| refactor | 동작은 그대로 두고 구조만 바꿀 때 |
| perf | 성능을 개선할 때 |
| test | 테스트나 평가 세트를 추가·수정할 때 |
| docs | 문서만 바꿀 때 |
| chore | 빌드, 설정, 의존성, CI 등 그 밖의 작업 |

## scope

| scope | 대상 |
|---|---|
| api | API 서버 |
| worker | 워커 서버 |
| web | 프론트엔드 |
| pipeline | TextToSQL 파이프라인 (스키마 → SQL 생성 → 검증 → 실행) |
| eval | 정확도 평가 세트와 평가 스크립트 |
| infra | Docker, 배포, CI |
| 문서 이름 | docs 커밋일 때: `prd`, `roadmap`, `ia`, `architecture` 등 |

## 예시

```
feat(pipeline): 질문과 DB 스키마로 SELECT 문을 생성한다 (F-001)
fix(api): LIMIT 없는 SQL이 테이블 전체를 읽던 문제를 고친다 (F-002)
test(eval): 매출 데이터 대표 질문 30개와 정답 SQL을 추가한다
docs(prd): Must 기능 5개의 수용 기준을 확정한다
chore: api, worker, web 폴더 구조를 만든다
```

## 커밋 단위

- 한 커밋에는 한 가지 변경만 담는다. 기능을 만들다 생긴 리팩터링은 따로 커밋한다.
- 기능 단위로 자주 커밋해서 언제든 되돌릴 수 있게 한다.
